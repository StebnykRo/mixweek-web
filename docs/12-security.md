## 2. Секрети та конфігурація

### 2.1 Що лишається в `.env`

**Тільки bootstrap-мінімум** — те, без чого процес не може підняти
зʼєднання й розшифрувати решту:

```dotenv
NODE_ENV=production
APP_URL=https://app.example.com
DATABASE_URL=postgresql://app_user:...@host:5432/mixweek?sslmode=require
REDIS_URL=rediss://...
AUTH_SECRET=<32+ байти base64>          # підпис cookie/CSRF
APP_MASTER_KEY=<32 байти base64>        # KEK для envelope encryption
S3_ENDPOINT=https://...                 # без ключів
S3_BUCKET=mixweek-prod
```

Це все. **Жодного** SMTP-пароля, Google client secret, VAPID-ключа, S3
access key, Sentry DSN чи API-ключа Maps у `.env`.

Правила для `.env`:
- права `600`, власник — користувач сервісу;
- `.env*` у `.gitignore`, `.env.example` містить лише імена й формат;
- у контейнері монтується як read-only secret, не як шар образу;
- валідація Zod у `src/lib/env.ts`, fail-fast з переліком відсутніх ключів
  (без значень у повідомленні);
- у проді `APP_MASTER_KEY` бажано брати з KMS/Vault/секрет-менеджера
  хостингу, а не з файлу — код читає його через один інтерфейс
  `getMasterKey()`, тому заміна джерела не зачіпає застосунок.

### 2.2 Усе інше — зашифровано в БД

**Envelope encryption:**

```
APP_MASTER_KEY (KEK, 32 байти)
   └─ обгортає DEK (унікальний на кожен секрет, 32 байти, CSPRNG)
        └─ шифрує значення: AES-256-GCM (iv 12 байт, authTag 16 байт)
             └─ AAD = `${tenantId ?? 'platform'}:${key}:${keyVersion}`
```

AAD прив'язує шифротекст до його місця: перенесений рядок з іншого
тенанта не розшифрується.

```ts
// src/lib/crypto/secrets.ts
export async function setSecret(scope, key, plaintext, actor): Promise<void>
export async function getSecret(key: SecretKey, scope?): Promise<string>
export async function rotateSecret(key, newPlaintext, actor): Promise<void>
export async function deleteSecret(key, actor): Promise<void>
```

Правила:
- `getSecret()` — **єдиний** дозволений спосіб отримати секрет у рантаймі.
  Прямий доступ до `SecretSetting` поза `src/lib/crypto/*` заборонений
  лінт-правилом.
- In-memory кеш 60 с, ключі зберігаються у `Buffer`, після використання
  затираються (`buf.fill(0)`), не потрапляють у replay Sentry чи логи.
- **Читання назад у UI/API неможливе.** Адмін бачить лише `hint`
  (останні 4 символи), дату ротації й автора. Ендпоінт, що повертає
  значення, не існує — це не забутий функціонал, а рішення.
- Ротація: нове значення записується з `keyVersion + 1`, старе лишається
  24 год для graceful-переходу, потім видаляється фоновою задачею.
- Ротація `APP_MASTER_KEY`: команда `pnpm secrets:rewrap` перешифровує всі
  DEK новим KEK у транзакції; підтримується два активних KEK на час
  переходу (`APP_MASTER_KEY`, `APP_MASTER_KEY_PREVIOUS`).
- `expiresAt` + попередження в адмінці за 14 днів.
- Кожна операція з секретом → `AuditLog` (без значення) + step-up 2FA.

**Реєстр очікуваних ключів** (`SecretKey` union type, не довільні рядки):
```
mail.smtp_password · mail.resend_api_key
google.client_id · google.client_secret
push.vapid_public · push.vapid_private
s3.access_key_id · s3.secret_access_key
maps.api_key · sentry.dsn
analytics.pepper · checkin.signing_key · pickup.signing_key
webhook.<name>.secret · integration.<name>.token
```

`analytics.pepper` ротується раз на рік (розриває звʼязок історичних
подій з користувачем — це навмисно). `checkin.signing_key` і
`pickup.signing_key` підписують короткоживучі QR-токени.

### 2.3 Інші чутливі значення в БД

Так само шифруються (той самий модуль, ті самі правила):
- `AuthFactor.secretEnc` — TOTP-секрети;
- `Account.accessTokenEnc` / `refreshTokenEnc` — OAuth-токени;
- будь-які майбутні токени інтеграцій.

Хешуються (не шифруються — їх не треба відновлювати):
- токени сесій (SHA-256), magic link / OTP (SHA-256),
  recovery-коди (argon2id), коди чек-іну й видачі (SHA-256),
  IP та email в аналітиці (HMAC-SHA256 з окремим `analytics.pepper`).

**Ніколи не зберігаємо у відкритому вигляді:** сирі токени, сирі IP у
довгостроковому зберіганні, будь-які паролі (їх у системі немає).

## 3. Захист транспорту й HTTP-заголовки

Обов'язкові заголовки на **всіх** відповідях (middleware, покрито тестом):

```
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
Content-Security-Policy: <див. нижче>
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(self), microphone=(), geolocation=(self),
                    payment=(), usb=(), interest-cohort=()
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Resource-Policy: same-site
Cross-Origin-Embedder-Policy: credentialless
```

`camera=(self)` — потрібна лише для сканера QR в адмінці;
`geolocation=(self)` — для «прокласти маршрут», запитується явно.

### CSP (без `unsafe-inline` і `unsafe-eval`)

```
default-src 'self';
script-src 'self' 'nonce-{RANDOM}' 'strict-dynamic';
style-src 'self' 'nonce-{RANDOM}' https://fonts.googleapis.com;
font-src 'self' https://fonts.gstatic.com data:;
img-src 'self' data: blob: https://cdn.example.com;
connect-src 'self' https://sentry.example.com;
frame-src 'none';          /* див. примітку про embed нижче */
frame-ancestors 'none';
form-action 'self';
base-uri 'self';
object-src 'none';
worker-src 'self';
manifest-src 'self';
upgrade-insecure-requests;
report-to csp-endpoint;
```

- Nonce генерується на кожен запит у middleware, передається в `<script>`
  і в інлайновий `<style>` бренду.
- **`frame-src` — динамічний.** База — `'none'`. Директива розширюється
  рівно на ті домени, які увімкнені фіче-флагами:
  `map.google` → `https://www.google.com/maps/embed/` ·
  `media.embed` → `https://www.youtube-nocookie.com https://player.vimeo.com`.
  Дефолтна конфігурація v1 (мапа зображенням, медіа посиланням) лишає
  `frame-src 'none'`. Домени задаються константою в коді, не з БД —
  тенант не може розширити CSP.
- **`brandPreview` в адмінці** використовує `<iframe sandbox>` з тим самим
  origin, тому `frame-src 'self'` додається лише на маршрутах `/admin/*`.
- Домени шрифтів прибираються, якщо тенант обрав self-hosted.
- **Реалізація (2026-08):** до політики додано
  `style-src-attr 'unsafe-inline'`. `style-src` лишається nonce-only, тобто
  ін'єкція `<style>` неможлива. Директива `style-src-attr` стосується лише
  атрибута `style=""`, який React використовує для справді динамічних значень
  (координати пінів мапи у відсотках, ширина `CapacityMeter`, розмір лого).
  CSP Level 3 блокує атрибути стилю, щойно в `style-src` з'являється nonce, а
  механізму nonce для атрибута не існує. React екранує значення атрибутів, і
  атрибут не може виконати скрипт. `script-src` не змінено. Деталі —
  `docs/DELIVERY-NOTES.md` §1.2.
- **Реалізація:** `/sw.js` винесено з-під `middleware.ts` і віддається з
  власною політикою `default-src 'self'; script-src 'self'` — service worker
  керується CSP власної відповіді й не може нести nonce.
- Спершу викочується `Content-Security-Policy-Report-Only` на 1 тиждень,
  збираються звіти, потім вмикається в блокуючому режимі.
- Порушення CSP збираються на `/api/csp-report` (rate-limited) і йдуть у
  логи з алертом при сплеску.

### TLS
TLS 1.2+ (бажано 1.3), сучасні шифри, HSTS preload, автоматичне оновлення
сертифікатів, OCSP stapling. HTTP → 301 на HTTPS. `sslmode=require` для
зʼєднання з Postgres, TLS для Redis.

## 4. Автентифікація та сесії

Повністю описано в `docs/03-auth.md`. Критичні пункти для перевірки:

- Паролів немає — немає й ризику їх витоку/повторного використання.
- Токени: 32 байти CSPRNG, base64url, у БД лише SHA-256.
- Cookie: `__Host-mw.session`, `HttpOnly`, `Secure`, `SameSite=Lax`.
- Ротація токена сесії після 2FA і при зміні привілеїв.
- 2FA обов'язкова для всіх ролей ≥ `SUPPORT` (дефолт `REQUIRED_STAFF`).
- Step-up для чутливих дій (§ `docs/03` п.5).
- Миттєвий revoke сесій; авто-revoke при зміні ролі/email/2FA.
- Сповіщення email при: вході з нового пристрою, зміні 2FA,
  використанні recovery-коду, зміні ролі.
- Constant-time порівняння всіх токенів (`crypto.timingSafeEqual`).

## 5. Авторизація

- Deny-by-default. Кожна операція проходить `can(session, action, resource)`.
- Перевірка **завжди на сервері**; приховування UI — це не захист.
- Об'єкти перевіряються за `(tenantId, id)`, ніколи лише за `id`.
- Немає доступу → `404` (не розкриваємо існування).
- Server Actions і route handlers перевіряються **однаково** — Server
  Action це публічний ендпоінт, а не «внутрішній виклик». Це найчастіша
  помилка в Next.js-проєктах: кожна Server Action починається з
  `authorize()`.
- Тест: автоматичний прохід по всіх зареєстрованих маршрутах перевіряє, що
  анонімний запит отримує 401/404, а не 200.

## 6. Валідація входу й вихідне кодування

- Zod на межі, `strictObject`, явні `max()` на рядках і масивах.
- Ліміти: тіло ≤ 256 КБ, файл ≤ 10 МБ, глибина JSON ≤ 10, масив ≤ 500.
- Параметри маршруту валідуються як cuid2, не як довільний рядок.
- Вихід: React екранує за замовчуванням; `dangerouslySetInnerHTML` —
  тільки для Markdown після `rehype-sanitize` з allowlist тегів
  (`p, br, strong, em, ul, ol, li, a, h2..h4, blockquote, code, pre`) і
  атрибутів (`href` лише `https:`/`mailto:`/`tel:`).
- Заборонені: `eval`, `new Function`, динамічний `import()` зі змінної,
  конкатенація SQL. Prisma-`$queryRawUnsafe` заборонений лінтом;
  `$queryRaw` — тільки з тегованими шаблонами.
- Редиректи: тільки на відносні шляхи або на allowlist доменів
  (захист від open redirect у `?next=`).

## 7. Завантаження файлів

Єдині завантаження в v1: **лого брендів**, **обкладинки медіа**,
**зображення плану мапи** та **обкладинки івентів і товарів** — усе це
робить адміністратор в адмінці. **Учасники не завантажують нічого**:
ні фото (`docs/08`), ні аватари (ініціали замість фото, `docs/07` §2).
Це прибирає цілий клас загроз разом із потребою модерувати вміст.

- Приймаємо: JPEG, PNG, WebP, AVIF (обкладинки); + SVG (тільки лого).
- Перевірка **magic bytes**, не `Content-Type` і не розширення.
- Розмір ≤ 10 МБ, розміри ≤ 8000×8000 (захист від decompression bomb).
- Растр: повне перекодування через `sharp` → знищує будь-який вбудований
  активний вміст; видалення всіх метаданих (`.withMetadata({})`).
- SVG: `svgo` + DOMPurify у режимі SVG — видалення `<script>`,
  `<foreignObject>`, `<use href="http…">`, усіх `on*`, `href="javascript:"`.
  Якщо після санітизації файл змінився критично — відхиляємо.
- Імена файлів генерує сервер (cuid2). Оригінальне ім'я зберігається лише
  як метадані для відображення, екранується.
- Віддача — з окремого домену (`cdn.…`) з
  `Content-Security-Policy: sandbox` і `X-Content-Type-Options: nosniff`.
- Антивірусне сканування (ClamAV) — опційно, вмикається фіче-флагом
  `security.av_scan` для тенантів з підвищеними вимогами.

## 8. Rate limiting і стійкість

Багаторівневий: CDN/WAF (L7, груба фільтрація) → middleware (по IP) →
handler (по користувачу/дії).

Ліміти — `docs/03-auth.md` §7 і `docs/09-api.md`.
Реалізація: Redis, sliding window, fail-**closed** для критичних
ендпоінтів автентифікації (якщо Redis недоступний — відмовляємо, не
пропускаємо) і fail-open для читання контенту.

Додатково:
- Ліміт одночасних сесій: 10 на користувача.
- Ліміт розміру відповіді й часу виконання (30 с) на запит.
- Circuit breaker на зовнішні виклики (пошта, push) з деградацією.
- Асинхронні важкі операції (експорт, розсилка) — тільки через черги.

## 9. Логування, PII і приватність

**Ніколи не логуємо:** токени будь-якого виду, cookie, OTP, magic link,
секрети, TOTP-коди, повний email (тільки `a***@domain.com`), повні IP
(тільки HMAC або /24-агрегат), тіла запитів з персональними даними,
відповіді форм реєстрації.

**Логуємо завжди:** `requestId`, `tenantId`, псевдонімізований `userId`,
маршрут, метод, статус, тривалість, розмір.

- Скрабер працює на рівні логера (allowlist полів), а не «не забути».
- Sentry: `beforeSend` вирізає PII, `sendDefaultPii: false`, маскування
  введених даних у replay вимкнено разом із самим replay для екранів
  автентифікації.
- Термін зберігання логів — 30 днів (90 для security-подій).
- Доступ до логів — тільки для DevOps-ролі, з аудитом.

## 10. GDPR і робота з персональними даними

| Вимога | Реалізація |
|---|---|
| Правова підстава | договір (участь в івенті) + згода (пуші, фото, дієтичні уподобання) |
| Мінімізація | збираємо тільки те, що потрібно для проведення івенту |
| Прозорість | Privacy Policy з версією, `Consent` фіксує версію й час |
| Право доступу | `/profile/privacy` → експорт ZIP (JSON) за 24 год |
| Право на видалення | запит → 30 днів grace → жорстке видалення + анонімізація історії |
| Право на виправлення | редагування профілю; решта — через підтримку |
| Обмеження зберігання | політики з `docs/02` §5, автоматична чистка |
| Захист за замовчуванням | шифрування at-rest (диски БД і S3), TLS in-transit |
| Реєстр обробки (ROPA) | зовнішній документ замовника; ТЗ фіксує перелік категорій даних і термінів (`docs/02` §5) як вхідні дані для нього |
| Субпроцесори | перелік у Privacy Policy: хостинг, пошта, Sentry, CDN |
| Транскордонна передача | усі сервіси в ЄС (регіон EU) — вимога до вибору провайдерів |
| DPIA | потрібна, якщо додається біометрія/геолокація — у v1 не потрібна |

**Мінімізація на практиці:**
- Не зберігаємо сирі IP довше 24 год.
- Не збираємо дату народження, домашню адресу, паспортні дані.
- Дієтичні уподобання — з окремим поясненням і видаленням після івенту.
- Фото — не зберігаємо взагалі (`docs/08`).

## 11. Безпека залежностей і збірки

- `pnpm` з lock-файлом; `enable-pre-post-scripts=false` (жодних
  postinstall-скриптів).
- CI: `pnpm audit --audit-level=high` (блокує), Semgrep з правилами
  `javascript.express`, `typescript.react`, `owasp-top-ten`,
  Trivy для образу, secret-scanning (gitleaks) на кожен коміт і в історії.
- Renovate: автоматичні PR, security-оновлення з високим пріоритетом.
- SBOM (CycloneDX) генерується на кожен реліз і зберігається.
- Образ: multi-stage, distroless/alpine, non-root UID, read-only rootfs,
  без shell у фінальному шарі, `NODE_ENV=production`.
- Заборонені пакети: усе, що виконує мережеві запити при встановленні;
  усе з < 10k тижневих завантажень без явного погодження.
- `next.config`: `poweredByHeader: false`, `productionBrowserSourceMaps:
  false` (мапи вивантажуються в Sentry, не публічно).

## 12. Інфраструктура

- Postgres і Redis **не мають публічних адрес** — тільки приватна мережа.
- Застосунок ходить у БД під роллю `app_user` без `SUPERUSER`,
  без `BYPASSRLS`, з правами тільки на потрібні таблиці.
- Окремі облікові записи для міграцій (CI) і для рантайму.
- SSH — тільки по ключах, без пароля, з bastion; краще — взагалі без SSH
  (immutable-інфраструктура).
- Шифрування дисків at-rest для БД, бекапів і S3.
- Бекапи зашифровані окремим ключем, що зберігається не поруч із бекапом.
- Розділення середовищ: окремі мережі, окремі БД, окремі ключі. Прод-дані
  не потрапляють у staging без анонімізації.
- WAF: базові правила OWASP CRS + гео/бот-фільтрація за потреби.

## 13. Реагування на інциденти

1. **Виявлення**: алерти (сплеск 5xx, сплеск невдалих логінів, CSP-звіти,
   аномальні експорти, падіння черг).
2. **Класифікація**: P1 (витік даних / компрометація) · P2 (недоступність) ·
   P3 (деградація).
3. **Стримування** (готові команди, задокументовані):
   - `pnpm ops:revoke-sessions --user=<id> | --tenant=<id> | --all`
   - `pnpm ops:rotate-secret --key=<key>`
   - `pnpm ops:disable-tenant --id=<id>`
   - вимкнення фіче-флага без деплою.
4. **Комунікація**: при витоку персональних даних — повідомлення
   наглядового органу протягом **72 годин** (GDPR ст. 33) і суб'єктам
   даних, якщо високий ризик. Шаблон листа готує юридична служба
   замовника до релізу — це не артефакт розробки, але без нього
   реліз-чекліст §15 не закривається.
5. **Постмортем** без пошуку винних, з конкретними діями й термінами.

Контакти й ескалація фіксуються замовником до релізу.
