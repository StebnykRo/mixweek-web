# 06 · Івенти: життєвий цикл, минулі/майбутні, реєстрація

## 1. Дві сутності, які не можна плутати

- **Event** — подія-парасолька («Mix Week 2026», 21–27.10, Лімасол).
  На неї **реєструються**.
- **Activity** — пункт програми всередині івенту (воркшоп, турнір,
  Gala Night). Її можна **зберегти в свою програму (♥)** і, якщо є ліміт
  місць, **забронювати**.

## 2. Життєвий цикл Event

```
DRAFT ──publish──► PUBLISHED ──(endsAt пройшов)──► [past] ──archive──► ARCHIVED
  │                    │
  └──delete──►         └──cancel──► CANCELLED
```

`status` — керований адміном. **Часовий стан обчислюється, не зберігається:**

```ts
type EventPhase = 'upcoming' | 'live' | 'past';
// upcoming: now < startsAt
// live:     startsAt <= now <= endsAt
// past:     now > endsAt
```

Обчислення робиться в **таймзоні івенту** (`Event.timezone`), не браузера і
не сервера. Це джерело найпоширенішого класу багів — покривається
unit-тестами з фіксованим `now` для трьох таймзон.

Правила видимості:
| status | phase | видно учаснику |
|---|---|---|
| DRAFT | будь-яка | ні (лише адмінка) |
| PUBLISHED | upcoming | так, у «Майбутні», реєстрація за вікном |
| PUBLISHED | live | так, «Зараз іде», повна програма |
| PUBLISHED | past | так, у «Минулі», read-only + медіа |
| ARCHIVED | past | так, у «Минулі», read-only, без нотифікацій |
| CANCELLED | будь-яка | так, з явним бейджем «Скасовано» |

## 3. Екран «Івенти»

Три вкладки: **Майбутні** · **Минулі** · **Мої**.

- **Майбутні** — `PUBLISHED`, `startsAt > now`, відсортовані за `startsAt` ↑.
  Картка: обкладинка, назва, дати, місто, бейдж стану реєстрації
  («Реєстрація відкрита до 10 жовтня» / «Ви зареєстровані» /
  «Лист очікування» / «Реєстрація закрита» / «Місць немає»).
- **Минулі** — `startsAt` ↓. Картка приглушена, бейдж «Ви були» якщо
  `ATTENDED`, і бейдж «Фото» якщо є опубліковані `MediaLink`.
- **Мої** — усе, де є активна реєстрація, згруповано «Найближчі» / «Минулі».

Фільтри: рік, місто, тип (за тегами), «тільки мої».
Пошук за назвою (trigram-індекс).
Пагінація — курсорна, 20 на сторінку, infinite scroll на мобільному й
кнопка «Показати ще» на десктопі (доступність).

Якщо у тенанта рівно один активний івент — застосунок **відкривається
одразу на ньому**, а список доступний через перемикач у навігації. Не
змушуємо клікати зайвий раз.

## 4. Реєстрація на івент

### 4.1 Вікно й умови

```
registrationEnabled && status == PUBLISHED
&& (registrationOpensAt  == null || now >= registrationOpensAt)
&& (registrationClosesAt == null || now <= registrationClosesAt)
&& userMatchesVisibility(event, user)
```

`visibility`:
- `TENANT` — усі активні учасники тенанта;
- `INVITE_ONLY` — лише ті, у кого є `Invite` на цей івент;
- `GROUP` — за правилами аудиторії (`audienceRules`: департаменти, команди,
  ролі).

### 4.2 Форма реєстрації

`Event.registrationForm` — JSON-схема полів, редагована в адмінці:

```json
{
  "fields": [
    { "key": "arrivalDate",  "type": "date",     "label": {"en":"Arrival date"}, "required": true },
    { "key": "dietary",      "type": "select",   "label": {"en":"Dietary preference"},
      "options": ["none","vegetarian","vegan","gluten-free"], "required": false },
    { "key": "tshirtSize",   "type": "select",   "options": ["S","M","L","XL"] },
    { "key": "needsTransfer","type": "boolean",  "label": {"en":"Airport transfer needed"} },
    { "key": "notes",        "type": "textarea", "maxLength": 500 }
  ]
}
```

Підтримувані типи: `text`, `textarea`, `number`, `date`, `select`,
`multiselect`, `boolean`, `consent`. Zod-схема генерується з цього JSON
**на сервері** і валідує відповіді там же. Клієнтська валідація —
дублююча, не єдина.

**Заборонено** збирати спеціальні категорії даних (здоров'я, релігія) як
вільний текст без явної згоди — поле `dietary` супроводжується поясненням
призначення й терміну зберігання. Медичні дані в v1 не збираємо взагалі.

### 4.3 Логіка місткості й waitlist

Ключова вимога — **немає овербукінгу при одночасних запитах**.

```sql
-- Усередині SERIALIZABLE-транзакції або з блокуванням рядка івенту
SELECT capacity FROM "Event" WHERE id = $1 FOR UPDATE;
SELECT count(*) FROM "EventRegistration"
  WHERE "eventId" = $1 AND status IN ('CONFIRMED','PENDING');
```

Алгоритм:
1. Транзакція, `SELECT ... FOR UPDATE` на рядку `Event`.
2. Якщо `capacity == null` або вільні місця є → `CONFIRMED`
   (або `PENDING`, якщо `approvalRequired`).
3. Інакше, якщо `waitlistEnabled` → `WAITLISTED` з
   `waitlistPosition = max + 1`.
4. Інакше → помилка `EVENT_FULL`.
5. Унікальний частковий індекс `registration_active_uniq` (див. `docs/02`)
   робить подвійну реєстрацію неможливою навіть при гонці.

Скасування → фонова задача `waitlist:promote`:
бере першого в черзі, переводить у `CONFIRMED`, шле пуш+email
«Місце звільнилося», перенумеровує чергу. Якщо користувач не підтвердив
протягом 24 год (для івентів з `approvalRequired`) — місце йде далі.

### 4.4 Модерація (`approvalRequired`)

`PENDING` → адмін підтверджує/відхиляє в адмінці, масові дії підтримуються.
Кожна зміна статусу → нотифікація користувачу.

### 4.5 Скасування учасником

Дозволене до `registrationClosesAt` або до `startsAt` (налаштування).
Після — тільки через підтримку. Скасування звільняє місце й тригерить
waitlist.

### 4.6 Чек-ін

Два режими, обидва перевіряються сканером в адмінці (`EVENT_MANAGER`),
який ставить `ATTENDED`:

**Онлайн (основний).** QR містить **короткоживучий підписаний токен**
(JWT, TTL 60 с, `aud=checkin`, `sub=registrationId`), що оновлюється
кожні 30 с на екрані. Скріншот чужого QR стає непридатним за хвилину.

**Офлайн (резервний).** Якщо телефон учасника без мережі, показується
статичний код, похідний від `checkInCodeHash` (6 символів, base32).
Він **не** короткоживучий, тому:
- приймається лише в межах дат івенту;
- одноразовий — повторне сканування дає «вже зареєстровано» з часом
  першого чек-іну;
- сканер логує режим (`online` / `offline_code`) в `AuditLog`;
- сам код не кешується service worker-ом як відповідь API, а
  обчислюється на клієнті з даних реєстрації (`docs/13` §4).

Це свідомий компроміс: інтернет на майданчику ненадійний, а черга на
вході — гірша проблема, ніж теоретичне передавання коду колезі.

## 5. Бронювання активностей

Для `Activity.bookingRequired = true`:
- та сама транзакційна логіка місткості й waitlist;
- `CapacityMeter` показує «12 / 40» і «в черзі: 3»;
- конфлікт у розкладі (перетин часу з уже забронюваним) → попередження, але
  не блокування («У вас уже є подія в цей час»);
- нагадування за 24 год і за 15 хв до початку;
- скасування бронювання ≥ 2 год до початку (налаштовується).

Для решти активностей — лише `SavedActivity` (♥), без обмежень.

## 6. «Моя програма»

Обʼєднання `SavedActivity` + `ActivityBooking(BOOKED)` + активності, на які
користувач зареєстрований примусово (`isMandatory` — окремий прапорець на
`Activity`, додається у фазі 3, якщо потрібен).

- Сортування за часом, групування по днях.
- Позначки: ♥ збережено · ✓ заброньовано · ⏳ у черзі.
- Експорт: **.ics** (весь список або одна активність) — важливо, бо це
  замінює «інтеграцію з календарем» без нативного застосунку.
  `GET /api/v1/events/{id}/my-schedule.ics` з підписаним одноразовим
  токеном; окремо — підписна URL з ротацією (для авто-оновлення).
- Конфлікти часу підсвічуються.

## 7. Зміни в програмі

При зміні `startsAt`/`endsAt`/`placeId` опублікованої активності адмінка
**обов'язково** питає: «Повідомити учасників?» з передзаповненим текстом.

- `Activity.status = MOVED`, `changeNote` = «Перенесено з 13:00 на 15:00».
- Бейдж «Змінено» в списку протягом 24 год.
- Нотифікація йде **тільки** тим, у кого ця активність у «Моїй програмі»
  або в бронюваннях — не всім підряд.
- Скасування: `CANCELLED`, активність лишається в списку закресленою,
  бронювання переводяться в `CANCELLED`, усім броньованим — пуш+email.

## 8. «Зараз» і «Далі» на Home

```ts
now  = activities.filter(a => a.startsAt <= t && t <= a.endsAt && a.status !== 'CANCELLED')
next = activities.filter(a => a.startsAt > t).slice(0, 3)
```

Пріоритет у «Зараз»: заброньовані → збережені → featured → решта.
Якщо нічого не йде: показуємо наступну активність з таймером «через 1 год
20 хв». Якщо івент ще не почався — зворотний відлік до старту. Якщо
завершився — блок «Дякуємо!» + посилання на фото (`docs/08`).

Обчислення робиться на клієнті з даних кешованої програми + серверного
`now` (щоб не залежати від годинника пристрою; сервер віддає `serverTime` у
відповіді). Оновлення щохвилини.

## 9. Минулий івент (recap)

Сторінка минулого івенту показує:
1. Підсумкові цифри (учасників, активностей, міст) — з агрегатів.
2. **Медіа** — картки галерей (`docs/08`), найпомітніший блок.
3. Програма в read-only з позначками «ви були».
4. Матеріали (презентації, записи) — `MediaKind.MATERIALS`.
5. Кнопка «Наступний івент →», якщо є майбутній.

Реєстрація, бронювання, резерв мерчу — вимкнені. Пуші по цьому івенту не
надсилаються.

## 10. Тести розділу

1. Овербукінг: 50 паралельних реєстрацій на 10 місць → рівно 10
   `CONFIRMED`, 40 `WAITLISTED`, жодної помилки цілісності.
2. Скасування підвищує рівно одного з черги, позиції перенумеровані.
3. Фаза івенту правильно обчислюється для таймзон
   `Asia/Nicosia`, `Europe/Kyiv`, `America/New_York` на межах доби.
4. Реєстрація поза вікном → 422 з кодом `REGISTRATION_CLOSED`.
5. `INVITE_ONLY` без інвайту → 404.
6. Відповіді форми валідуються на сервері; зайві поля відкидаються.
7. `.ics` імпортується в Google Calendar і Apple Calendar без помилок.
8. Перенесення активності шле нотифікацію лише зацікавленим.
9. Минулий івент: усі мутуючі ендпоінти повертають 409 `EVENT_ENDED`.
10. QR чек-іну недійсний через 60 секунд після видачі токена.
11. Офлайн-код чек-іну приймається сканером і не приймається двічі.
