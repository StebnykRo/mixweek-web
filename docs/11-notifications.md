# 11 · Нотифікації

## 1. Канали

| Канал | Технологія | Роль |
|---|---|---|
| **Web Push** | Web Push API + VAPID, власний сервер (без FCM/APNs як посередників) | основний для термінових повідомлень |
| **Email** | Resend/SMTP | резерв і підтвердження; єдиний канал для тих, хто не дав дозвіл на пуші |
| **In-app** | `NotificationDelivery` + дзвіночок у хедері | історія, «прочитано» |
| **Announcement** | банер на Home | не потребує дозволу, бачать усі |

**Обмеження iOS, яке треба врахувати з першого дня:** web push у Safari
працює **лише** для PWA, доданої на екран «Додому» (iOS 16.4+). Тому:
- на iOS показуємо явну підказку «Додайте застосунок на екран «Додому»,
  щоб отримувати сповіщення» з покроковою інструкцією;
- для всіх, у кого пуш недоступний, критичні повідомлення **дублюються
  email-ом** автоматично;
- банер-оголошення на Home є завжди — це гарантований канал.

## 2. Типи повідомлень і дефолти

| Kind | Приклад | Push | Email | Можна вимкнути |
|---|---|---|---|---|
| `SCHEDULE_CHANGE` | «5×5 Football перенесено на 15:00» | ✅ | ✅ | ні (критичне) |
| `PROGRAMME_UPDATE` | «Додано 5 нових подій у програму» | ✅ | опційно | так |
| `REMINDER` | «Team Time за 15 хвилин · Workshop Hub» | ✅ | ні | так |
| `ANNOUNCEMENT` | «Автобуси від готелю о 17:30» | ✅ | опційно | так |
| `REGISTRATION` | «Реєстрацію підтверджено» / «Місце звільнилося» | ✅ | ✅ | ні |
| `MEDIA_READY` | «Фото з Mix Week готові» | ✅ | ✅ | так |
| `MERCH` | «Замовлення MW-0482 готове до видачі» | ✅ | ні | так |
| `SYSTEM` | «Новий вхід у ваш акаунт» | ні | ✅ | ні (безпека) |

Налаштування — `/profile/notifications`, зберігаються на сервері (не в
localStorage), застосовуються до всіх пристроїв.

## 3. Запит дозволу

- **Ніколи** не запитувати на першому екрані. Тригер: після першої
  осмисленої дії (додав активність у ♥, зареєструвався) або на 2-му візиті.
- Перед системним діалогом — власний екран-пояснення з кнопками
  «Увімкнути» / «Пізніше». Системний діалог викликається **тільки** після
  «Увімкнути» (браузер дає один шанс; витрачати його наосліп не можна).
- Якщо відмовили — більше не питаємо, показуємо ненав'язливий рядок у
  профілі з інструкцією, як увімкнути вручну.

## 4. Розсилка під 3 000 користувачів

Наївна відправка 3 000 пушів одномоментно = сплеск трафіку на застосунок
через 5–10 секунд і ризик rate-limit push-сервісів.

**Правила:**
1. Черга `notifications`, throughput **200 повідомлень/с**, конкурентність 10.
2. **Jitter** 0–90 с на отримувача для нетермінових типів — розмазує
   «push storm» (див. `docs/01` §4).
3. `SCHEDULE_CHANGE` і `REGISTRATION` — без jitter, максимальний пріоритет.
4. Дедуплікація: `jobId = notificationId:userId:channel`. Повторний запуск
   не створює дублів.
5. Ретраї: 3 спроби, backoff 1 хв / 5 хв / 30 хв.
6. Помилки `404`/`410` від push-сервісу → `PushSubscription.isValid = false`
   (підписка мертва, більше не пробуємо).
7. Обмеження: не більше **5 пушів на користувача на годину** і **15 на
   добу**, крім критичних. При перевищенні — злиття у зведене
   повідомлення.
8. «Тихі години» 23:00–08:00 за таймзоною івенту: нетермінові
   відкладаються до ранку. Критичні йдуть завжди.

## 5. Автоматичні нотифікації

| Тригер | Повідомлення | Аудиторія |
|---|---|---|
| Cron кожні 5 хв | нагадування за 15 хв до активності | у кого вона в «Моїй програмі»/броні |
| Cron щодня 20:00 | «Завтра: 4 події у вашій програмі» | зареєстровані на live-івент |
| Зміна часу/місця | `SCHEDULE_CHANGE` | зацікавлені в цій активності |
| Скасування активності | `SCHEDULE_CHANGE` | ті самі |
| Публікація нових активностей в опублікованому івенті | `PROGRAMME_UPDATE`, **агреговано** | зареєстровані на івент |
| Промоушен з waitlist | «Місце звільнилося» | конкретний користувач |
| Реєстрація підтверджена/відхилена | `REGISTRATION` | конкретний користувач |
| Публікація медіа | `MEDIA_READY` | учасники минулого івенту |
| Замовлення готове | `MERCH` | власник замовлення |
| Новий вхід з нового пристрою | `SYSTEM` (email) | власник акаунта |
| Відкриття реєстрації на новий івент | `ANNOUNCEMENT` | усі активні тенанта |

### Агрегація `PROGRAMME_UPDATE`

Наповнення програми — це десятки збережень підряд. Один пуш на кожну
нову активність неприпустимий.

- Нові активності в опублікованому івенті накопичуються у вікні **6 годин**
  (ключ агрегації `programme-update:{eventId}`).
- Після закриття вікна відправляється **одне** повідомлення:
  «Додано 5 нових подій у програму Mix Week» з посиланням на програму,
  відфільтровану за `?added=recent`.
- Якщо активність за цей час знову змінили або видалили — вона просто не
  потрапляє в підсумок.
- Адмін може відправити одразу («Повідомити зараз») або вимкнути
  сповіщення для конкретної партії змін.
- Вимкнено за замовчуванням для івентів у статусі `DRAFT` — там сповіщень
  немає взагалі.

## 6. Вміст повідомлення

- Заголовок ≤ 50 символів, тіло ≤ 120 (обрізається на Android/desktop).
- Іконка — `logoMarkUrl` бренду; badge — монохромна.
- `data.url` — глибоке посилання всередину застосунку
  (`/events/mix-week-2026/programme/abc123`).
- `tag` для групування (одна активність не спамить кілька разів),
  `renotify: false`.
- Локалізація за `User.locale`, з фолбеком на локаль тенанта.
- **У пуші немає персональних даних понад імʼя** — сповіщення видно на
  залоченому екрані.

## 7. Email

- Один HTML-шаблон, брендований під тенант (лого, кольори з `Brand`),
  з текстовою версією.
- Обов'язково: тема без спам-тригерів, prehedaer, посилання на застосунок,
  футер з причиною отримання й посиланням на налаштування.
- SPF + DKIM + DMARC (`p=reject`) на домені відправника.
- Транзакційні листи не містять маркетингу й не потребують unsubscribe,
  але посилання «Налаштування сповіщень» є завжди.
- Bounce/complaint-вебхуки → позначка проблемної адреси + сповіщення
  адміну.

## 8. Service Worker

```js
self.addEventListener('push', e => { /* показ нотифікації */ });
self.addEventListener('notificationclick', e => {
  // фокус на вже відкриту вкладку застосунку або відкриття нової на data.url
});
self.addEventListener('pushsubscriptionchange', e => {
  // автоматичне переоформлення підписки на сервері
});
```

Обробка `pushsubscriptionchange` обов'язкова — інакше підписки тихо
«вмирають» і частина людей перестає отримувати сповіщення без жодного
сигналу.

## 9. Безпека

- VAPID-ключі — у `SecretSetting`, приватний ключ ніколи не залишає
  сервер.
- Ендпоінт підписки прив'язується до `userId` і `tenantId`; неможливо
  зареєструвати підписку на чужого користувача.
- Payload шифрується стандартом Web Push (aes128gcm) — це вимога
  протоколу, не опція.
- Ліміт: 10 активних підписок на користувача, найстаріші витісняються.
- Адмін не бачить endpoint-и підписок (це ідентифікатор пристрою).
- Розсилка > 100 адресатів — step-up 2FA + запис в `AuditLog` з
  повним текстом і сегментом.

## 10. Тести

1. 3 000 доставок обробляються без падіння черги; jitter розподіляє їх у
   заданому вікні.
2. Повторний запуск тієї самої розсилки не створює дублікатів.
3. `410 Gone` вимикає підписку.
4. Тихі години відкладають нетермінові й пропускають критичні.
5. Ліміт 5/год спрацьовує й зливає повідомлення.
6. Вимкнений тип не доставляється; критичний доставляється попри
   налаштування.
7. Клік по пушу відкриває правильний глибокий маршрут.
8. Користувач тенанта A не може підписатися від імені користувача тенанта B.
