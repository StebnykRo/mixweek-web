# 03 · Автентифікація, 2FA та готовність до Google SSO

## 1. Рішення

**v1:** вхід за корпоративною поштою — **magic link + другий фактор**.
**v1.5:** Google OIDC додається як ще один провайдер **без міграції даних і
без зміни моделі** — усе необхідне закладено вже зараз.

Пароля в системі немає взагалі. Це навмисно: немає що вкрасти, немає
повторного використання паролів, немає скидання пароля як вектора атаки.

## 2. Схема входу (v1)

```
┌─ Крок 1 ─────────────────────────────────────────────────┐
│ Користувач вводить корпоративний email                    │
│ POST /api/v1/auth/start { email }                         │
│                                                           │
│ Сервер:                                                   │
│  1. нормалізує email (lowercase, trim, citext)            │
│  2. резолвить домен → TenantDomain → Tenant + Brand       │
│  3. rate-limit згідно з таблицею §7 (єдине джерело)        │
│  4. якщо домен невідомий → перевіряє активний Invite      │
│  5. створює VerificationToken(MAGIC_LINK) + (EMAIL_OTP)   │
│     • один лист містить і посилання, і 6-значний код      │
│     • TTL 10 хв, одноразові, maxAttempts 5                │
│     • bindingHash = HMAC(cookie `auth_binding`)           │
│  6. ЗАВЖДИ повертає 200 з однаковою відповіддю і однаковою │
│     затримкою (constant-time) — жодного user enumeration  │
│                                                           │
│ Відповідь містить brand (лого/кольори) ТІЛЬКИ якщо домен  │
│ верифікований і публічний — інакше нейтральний бренд.     │
└───────────────────────────────────────────────────────────┘
                            │
┌─ Крок 2 ──────────────────▼──────────────────────────────┐
│ A) Клік по magic link у пошті                            │
│    GET /auth/verify?token=...                            │
│    • якщо bindingHash збігається з cookie цього браузера  │
│      → вхід завершується одразу                          │
│    • якщо НІ (лист відкрито на іншому пристрої)          │
│      → показуємо код підтвердження, який треба ввести     │
│        у вкладці, де починався логін (anti-phishing)      │
│                                                          │
│ B) Введення 6-значного коду в тій самій вкладці          │
│    POST /api/v1/auth/verify { code }                     │
│    • 5 спроб, потім токен спалюється                     │
└──────────────────────────────────────────────────────────┘
                            │
┌─ Крок 3: другий фактор ───▼──────────────────────────────┐
│ Сесія створюється з mfaSatisfied = false.                │
│ Політика тенанта (`auth.mfa_policy`):                    │
│   • REQUIRED_ALL      — 2FA обов'язкова для всіх         │
│   • REQUIRED_STAFF    — обов'язкова для ролей ≥ SUPPORT  │
│                         (ДЕФОЛТ)                         │
│   • OPTIONAL          — користувач вмикає сам            │
│                                                          │
│ Якщо потрібна і не налаштована → примусовий екран        │
│ налаштування TOTP (QR + 10 recovery-кодів).              │
│ Якщо налаштована → запит 6-значного TOTP-коду.           │
│ Успіх → mfaSatisfied = true, сесія повноцінна.           │
│                                                          │
│ «Довіряти цьому пристрою 30 днів» → TrustedDevice        │
│ (окремий httpOnly-cookie, прив'язаний до userId+UA-хешу).│
└──────────────────────────────────────────────────────────┘
                            │
┌─ Крок 4: онбординг (перший вхід) ─────▼──────────────────┐
│ • прийняття Terms + Privacy → запис у Consent            │
│ • вибір мови                                             │
│ • запит дозволу на пуші (не одразу — після першого       │
│   корисного екрана, інакше відмова майже гарантована)    │
└──────────────────────────────────────────────────────────┘
```

### Обов'язково: жодного user enumeration

`/auth/start` повертає **ідентичну** відповідь і для існуючого, і для
неіснуючого користувача, і для забороненого домену. Різниця — лише в тому,
чи справді пішов лист. Час відповіді вирівнюється (мінімум 400 мс).
Це покривається окремим тестом.

## 3. Провайдерна абстракція (ключове для Google)

Уся автентифікація йде через один інтерфейс:

```ts
// src/modules/auth/providers/types.ts
export interface AuthProvider {
  id: 'email' | 'google' | 'saml';
  /** Чи доступний провайдер для цього тенанта (з TenantSetting). */
  isEnabledFor(tenantId: string): Promise<boolean>;
  /** Повертає нормалізований профіль після успішної верифікації. */
  authenticate(input: unknown): Promise<AuthResult>;
}

export type AuthResult = {
  email: string;
  emailVerified: boolean;
  name?: string;
  avatarUrl?: string;
  /** Google: hd-claim; email: домен пошти. Обидва → резолв тенанта. */
  hostedDomain?: string;
  externalAccount?: { provider: string; providerAccountId: string };
};
```

Далі — спільний конвеєр, однаковий для всіх провайдерів:

```
AuthResult
  → resolveTenant(hostedDomain | emailDomain)     // docs/04
  → assertDomainAllowed()                          // або активний Invite
  → upsertUser() + upsertMembership()
  → linkAccount() якщо є externalAccount
  → applyMfaPolicy()
  → createSession()
  → auditLog('auth.login')
```

**Що вже є в v1 заради Google:**

| Елемент | Стан у v1 |
|---|---|
| Таблиця `Account` (provider, providerAccountId, hostedDomain) | створена, порожня |
| `AuthProvider` інтерфейс і реєстр провайдерів | реалізований, один провайдер `email` |
| Резолв тенанта за `hostedDomain` | реалізований (використовує домен пошти) |
| Account linking за **верифікованим** email | реалізований, покритий тестом |
| Політика MFA поверх будь-якого провайдера | реалізована |
| Auth.js callbacks (`signIn`, `jwt`, `session`) без прив'язки до email | реалізовані |
| UI логіну з місцем під кнопку «Continue with Google» | верстка є, кнопка за фіче-флагом `auth.google` |
| Секрети `google.client_id` / `google.client_secret` | ключі в `SecretSetting` описані, значення порожні |

**Що потрібно зробити для вмикання Google (оцінка: 1 день):**
1. Створити OAuth-клієнт у Google Cloud, redirect URI
   `https://<app>/api/auth/callback/google`.
2. Записати `google.client_id` / `google.client_secret` у `SecretSetting`
   через адмінку.
3. Увімкнути фіче-флаг `auth.google` на тенанті.
4. За потреби обмежити `hd` — щоб приймалися лише акаунти
   корпоративних доменів тенанта.

**Правила безпеки при лінкуванні акаунтів (критично):**
- Автоматичне зв'язування Google-акаунта з існуючим користувачем дозволене
  **лише** якщо Google повернув `email_verified: true` **і** домен email
  збігається з верифікованим `TenantDomain`.
- В інших випадках — потрібне підтвердження через magic link на цю ж пошту.
- Це закриває класичну атаку «зареєструвати Google-акаунт на чужий email».

## 4. Сесії

- **Database sessions** (не JWT) — щоб мати миттєвий revoke.
- Cookie: `__Host-mw.session`, `HttpOnly`, `Secure`, `SameSite=Lax`,
  `Path=/`, без `Domain`.
  **Реалізація:** префікс `__Host-` застосовується лише там, де з'єднання може
  його нести (браузер відкидає такий cookie без HTTPS). Поза
  production/staging використовується `mw.session`; читаються обидва варіанти.
  Деталі — `docs/DELIVERY-NOTES.md` §1.4.
- У БД зберігається **тільки SHA-256 хеш** токена.
- Час життя: 7 днів ковзний (rolling), максимум 30 днів абсолютний.
  Для адмін-ролей: 12 год ковзний, 24 год абсолютний.
- Ротація токена сесії при підвищенні привілеїв і після проходження 2FA
  (захист від session fixation).
- Профіль → «Активні сесії»: список пристроїв, «вийти з усіх».
- Автоматичний revoke всіх сесій при: зміні ролі, зміні email, скиданні
  2FA, підозрі на компрометацію (адмін-дія).

## 5. Step-up автентифікація

Повторне підтвердження другим фактором (не старше 15 хв) вимагається для:
- зміни/скидання 2FA;
- перегляду й ротації секретів;
- зміни бренду в проді, публікації івенту, масової розсилки > 100 адресатів;
- експорту персональних даних, видалення користувача;
- зміни ролей.

## 6. Ролі та авторизація

Перевірка прав — **тільки** через `src/modules/auth/policies.ts`:

```ts
can(session, 'event:publish', { tenantId, eventId })
```

Правила:
- Дефолт — **заборонено**. Політика має явно дозволити.
- Перевірка на сервері завжди. UI-приховування кнопок — це UX, не безпека.
- `SUPER_ADMIN` не має неявного доступу до даних тенанта: щоб зайти в
  тенант, він робить явний «impersonate tenant», що логується в `AuditLog`
  і показує в UI постійний банер «Ви переглядаєте як SUPER_ADMIN».
- Імперсонація конкретного користувача заборонена.

Матриця прав — `docs/10-admin.md`.

## 7. Rate limiting і захист від зловживань

| Ендпоінт | Ліміт |
|---|---|
| `POST /auth/start` | 5/год на email · 20/год на IP · 3/хв на IP · 100/год на підмережу /24 |
| `POST /auth/verify` | 10/год на IP · 5 спроб на токен |
| `POST /auth/mfa/verify` | 5/15 хв на користувача, потім блок на 15 хв |
| `POST /auth/mfa/recovery` | 5/добу на користувача + email-сповіщення |
| решта API (автентиковані) | 120/хв на користувача |
| API без автентикації | 30/хв на IP |
| Адмін-мутації | 60/хв на користувача |

Реалізація — Redis, алгоритм sliding window, ключі
`rl:{scope}:{subject}:{window}`. При спрацюванні — `429` + `Retry-After`,
без деталей про причину.

Додатково:
- Прогресивна затримка після 3 невдалих спроб (100 мс → 2 с).
- Turnstile/hCaptcha на `/auth/start` вмикається автоматично, якщо з одного
  IP > 10 спроб за годину (фіче-флаг `auth.captcha`).
- Алерт при > 50 невдалих логінах/хв по тенанту.

## 8. Листи автентифікації

- Домен-відправник з SPF + DKIM + DMARC (`p=reject`).
- Тема й тіло **брендовані** під тенант (лого, кольори з `Brand`).
- Лист містить: посилання, 6-значний код, час дії, IP-регіон і пристрій
  запиту, фразу «якщо це були не ви — проігноруйте лист і повідомте
  <контакт>».
- Посилання одноразове, TTL 10 хв, працює лише в межах свого тенанта.
- **Не** використовувати скорочувачі URL і трекінгові редиректи (ламають
  довіру і безпеку).
- У листі немає жодних персональних даних, крім самої адреси.

## 9. Гості (не співробітники)

- Створюються тільки через `Invite` (адмінка), з роллю `GUEST`, прив'язкою
  до конкретного івенту й TTL 30 днів.
- Гість бачить лише той івент, на який запрошений; решта платформи — 404.
- Домен пошти гостя не додається в `TenantDomain`.

## 10. Вихід і видалення

- Вихід: інвалідація сесії в БД + очищення cookie + (опційно) «вийти з усіх
  пристроїв».
- Видалення акаунта: запит з профілю → `DataRequest(DELETE)` → 30 днів
  grace з можливістю скасувати → жорстке видалення персональних даних,
  анонімізація історичних записів (реєстрації лишаються як агрегати).
- Експорт даних: `DataRequest(EXPORT)` → ZIP з JSON + підписане посилання,
  дійсне 24 год, одноразове.

## 11. Тести, обов'язкові для цього розділу

1. Однакова відповідь і час для існуючого/неіснуючого email.
2. Токен не можна використати двічі; після TTL — недійсний.
3. Токен, виданий у тенанті A, не входить у тенант B.
4. Перевищення лімітів дає 429 і не витікає інформація.
5. Сесія без `mfaSatisfied` не має доступу до жодного захищеного ресурсу.
6. Ротація токена сесії після 2FA (старий токен недійсний).
7. Recovery-код одноразовий; використання надсилає сповіщення.
8. `GUEST` не бачить чужі івенти (404, не 403 — не розкриваємо існування).
9. Зміна ролі відкликає всі сесії користувача.
10. Google-провайдер (мок): лінкування без `email_verified` відхиляється.
