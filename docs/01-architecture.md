# 01 · Архітектура

## 1. Загальна схема

```
                    ┌──────────────────────────────────────┐
   Браузер          │  CDN / WAF (Cloudflare)              │
   (PWA, SW)  ────► │  TLS 1.3, HSTS, bot-mitigation,      │
                    │  rate-limit L7, кеш статики          │
                    └───────────────┬──────────────────────┘
                                    │
                    ┌───────────────▼──────────────────────┐
                    │  Next.js 15 (Node runtime)           │
                    │  ├ RSC + Route Handlers /api/v1      │
                    │  ├ Auth.js (database sessions)       │
                    │  ├ middleware: tenant+brand resolve, │
                    │  │  security headers, nonce для CSP  │
                    │  └ 2 інстанси за LB (stateless)      │
                    └──┬──────────────┬─────────────┬──────┘
                       │              │             │
         ┌─────────────▼───┐  ┌───────▼──────┐  ┌───▼─────────────┐
         │ PostgreSQL 16   │  │ Redis/Valkey │  │ S3-compatible   │
         │ + PgBouncer     │  │ rate-limit,  │  │ (R2/MinIO)      │
         │ RLS увімкнено   │  │ кеш, BullMQ  │  │ лого, обкладинки│
         └─────────────────┘  └───────┬──────┘  └─────────────────┘
                                      │
                              ┌───────▼────────┐
                              │ Worker (BullMQ)│
                              │ пуші, email,   │
                              │ waitlist, звіти│
                              └────────────────┘
```

Зовнішні сервіси: Resend/SMTP (пошта), Web Push (VAPID, без сторонніх
сервісів), Sentry (помилки), Grafana Cloud/Loki (логи, метрики),
Google Maps Static/Embed або власне зображення мапи.

## 2. Середовища

| Env | Призначення | Дані | Доступ |
|---|---|---|---|
| `local` | розробка | seed | розробник |
| `preview` | PR-прев'ю | seed, автоскидання | команда, basic-auth |
| `staging` | приймання, навантаження | анонімізована копія | команда + замовник, IP-allowlist |
| `production` | бойове | реальні | лише через CI |

**Реалізація (2026-08):** середовище визначається змінною `APP_ENV`
(`src/lib/app-env.ts`), бо `next start` примусово ставить
`NODE_ENV=production` незалежно від способу запуску. `APP_ENV` за
замовчуванням дорівнює `NODE_ENV`; «загартованими» вважаються лише
`production` і `staging`. Від неї залежать: транспорт пошти, префікс cookie
`__Host-` (потребує HTTPS), множник рейт-лімітів для e2e і заголовок
`noindex`.

Правила:
- Прод-дані **ніколи** не копіюються в нижні середовища без анонімізації
  (скрипт `pnpm db:anonymize`: пошта → `user{n}@example.test`, імена →
  фейкові, токени й секрети — обнуляються).
- `preview` і `staging` закриті `X-Robots-Tag: noindex` і basic-auth.
- Кожне середовище має власний `APP_MASTER_KEY` і власний набір секретів.

## 3. Рендеринг і кешування

| Тип сторінки | Стратегія |
|---|---|
| Логін, онбординг | SSR, `no-store` |
| Список івентів | RSC, `revalidate = 60`, тегований кеш `events:{tenantId}` |
| Сторінка івенту (програма, мапа, EventStyle) | RSC + `unstable_cache` з тегами `event:{id}`, `programme:{eventId}`; інвалідація з адмінки при публікації |
| «Моя програма», реєстрації, профіль | завжди динамічно, `no-store`, персональні дані **ніколи** не в CDN |
| Адмінка | повністю динамічна, `no-store`, `private` |
| `/api/v1/*` | `no-store`, крім публічних довідників з `ETag` |

**Критично:** будь-яка відповідь, що містить персональні дані, має
`Cache-Control: private, no-store` і `Vary: Cookie`. Перевіряється тестом.

Клієнтський кеш — TanStack Query: `staleTime` 60 с для програми, 0 для
персональних даних. Оптимістичні апдейти для «♥» і бронювань з відкатом.

## 4. Продуктивність під 1 500–3 000 користувачів

Профіль навантаження **не рівномірний**. Ключовий сценарій — **«push storm»**:
пуш «Gala Night за 15 хвилин» → до 3 000 людей відкривають застосунок
протягом 60 секунд.

| Метрика | Ціль |
|---|---|
| Піковий RPS (push storm) | 150 rps на динамічні маршрути, 600 rps на статику |
| p95 TTFB, кешована сторінка івенту | ≤ 200 мс |
| p95 API-відповідь | ≤ 300 мс |
| p99 API-відповідь | ≤ 800 мс |
| Помилки 5xx під піком | < 0.1 % |
| DB-з'єднання | ≤ 40 через PgBouncer (transaction pooling) |

Заходи:
- Програма івенту віддається з кешу і не б'є в БД на кожен запит.
- Персональний шар («♥», бронювання) — окремий легкий запит, що
  накладається на кешовану програму на клієнті. Не змішувати.
- Service Worker віддає останню відому програму миттєво
  (stale-while-revalidate) — під час storm більшість користувачів взагалі
  не доходить до сервера.
- Пуші розсилаються **хвилями** (BullMQ, 200 повідомлень/с, jitter 0–90 с)
  замість одномоментного залпу.
- Індекси — див. `docs/02-data-model.md`.

Ресурси прод-середовища (достатньо і з запасом ×3):
`app` 2 × (2 vCPU / 2 GB) · `worker` 1 × (1 vCPU / 1 GB) ·
`postgres` 2 vCPU / 8 GB / 50 GB SSD · `redis` 1 GB.

## 5. Конфігурація і секрети

Три рівні конфігурації:

1. **Bootstrap (`.env`)** — лише те, без чого процес не стартує.
   Канонічний перелік ключів — `docs/12-security.md` §2.1 (дублювати його
   в інших файлах заборонено). Валідація Zod у `src/lib/env.ts`, fail-fast.
2. **Секрети (БД, зашифровані)** — SMTP/Resend, Google OAuth client
   id/secret, VAPID пара, S3 access/secret, Sentry DSN, Maps API key,
   вебхуки. Таблиця `SecretSetting`, envelope encryption AES-256-GCM,
   KEK = `APP_MASTER_KEY` (або KMS у проді). Читання — `getSecret(key)`
   з in-memory кешем 60 с. Ротація і перегляд — в адмінці (значення
   **ніколи** не повертається назад у UI, лише маска + метадані).
   Деталі — `docs/12-security.md` §2.
3. **Налаштування (БД, відкрито)** — фіче-флаги, ліміти, тексти, бренд.
   Таблиці `FeatureFlag`, `TenantSetting`, `Brand`.

## 6. Фонові задачі (BullMQ)

| Черга | Задача | Тригер |
|---|---|---|
| `notifications` | розсилка push/email хвилями | адмінка, шедулер |
| `reminders` | нагадування «за 15 хв до активності» | cron кожні 5 хв |
| `waitlist` | автопромоушен з листа очікування | скасування броні |
| `media` | обробка обкладинок: перекодування, зняття EXIF, 1600/800/400 у WebP+AVIF, blurhash (`docs/08` §3) | завантаження обкладинки |
| `exports` | CSV/XLSX-експорт реєстрацій | адмінка |
| `maintenance` | чистка протермінованих токенів, сесій, аудиту | cron щогодини |
| `digest` | «фото з івенту готові», підсумки | адмінка |

Усі задачі ідемпотентні, з `jobId` = детермінований ключ, retry 3 з
експоненційним backoff, DLQ з алертом.

## 7. Спостережуваність

- **Логи**: структуровані JSON, обов'язкові поля `requestId`, `tenantId`,
  `userId` (псевдонімізований hash), `route`, `durationMs`, `status`.
  **Заборонено логувати**: паролі, токени, magic-link, OTP, вміст
  cookie, повний email (лише `a***@softswiss.com`).
- **Метрики**: RPS, latency p50/p95/p99, помилки, глибина черг, hit-rate
  кешу, кількість активних сесій, невдалі логіни.
- **Алерти**: 5xx > 1 % за 5 хв · p95 > 1 с за 10 хв · черга > 1 000 ·
  сплеск невдалих логінів (> 50/хв) · падіння воркера · < 20 % вільного
  місця на диску БД.
- **Sentry**: source maps приховані, PII-скрабер увімкнений.

## 8. Резервне копіювання і відновлення

- PITR Postgres, повний бекап щодня, WAL безперервно, зберігання 30 днів.
- Бекапи зашифровані, ключ окремо від бекапу.
- **RPO ≤ 15 хв, RTO ≤ 2 год.**
- Раз на квартал — тестове відновлення на staging із записом результату.
- S3-бакет: версіонування + lifecycle 90 днів для видалених обʼєктів.

## 9. Деплой і CI/CD

Пайплайн: `lint → typecheck → unit → build → e2e (mobile+desktop) → a11y →
pnpm audit + semgrep → міграції (deploy) → rolling deploy → smoke → нотифікація`.

- Міграції запускаються окремим job до деплою, тільки forward-сумісні
  (expand/contract: спершу додаємо, деплоїмо, потім видаляємо старе).
- Rollback: попередній образ + `migrate resolve`. Деструктивні міграції
  вимагають ручного підтвердження.
- Секрети CI — в сховищі CI, з OIDC-доступом, без довгоживучих ключів.
- Образи скануються (Trivy), база — distroless/alpine, non-root user,
  read-only rootfs.

## 10. Готовність до майбутнього (не реалізуємо, але не блокуємо)

- **Google OIDC** — `Account`-таблиця й провайдер-абстракція вже в v1
  (`docs/03-auth.md`).
- **SAML/AD** — той самий провайдерний шар.
- **Нативний застосунок** — уся логіка вже за REST `/api/v1`, версіонованим
  і задокументованим (OpenAPI генерується з Zod).
- **Платежі WinStyle** — модель `Order` має статуси й поля під платіж.
- **Власне сховище фото** — `docs/08-media.md` описує фіче-флаг
  `media.self_hosted_upload`, схема під нього готова.
